# 上下文管理原理（30 分钟速读）

> 配套代码：`core/context_builder.py`　配套测试：`tests/test_context_builder.py`（12 个用例）
> 一句话：**压缩的本质不是"变短"，是"在有限 token 里保住不可重建的信息"。**

---

## 一、先想清楚：什么信息是不可重建的

这是所有取舍的源头。把消息分成三类：

| 类别 | 例子 | 能重新拿到吗 | 压缩策略 |
|---|---|---|---|
| **意图类** | 用户原始请求、确认过的参数 | ❌ 只有一次 | **永不压** |
| **决策类** | 助手决定先备份再改 | ❌ 是过程记录 | 尽量保原文 |
| **结果类** | 网页正文、文件内容、命令输出 | ✅ 可以再取一次 | **优先压** |

**判断标准只有一句**：如果删掉它，还能不能重新拿到？能，就压；不能，就留。

---

## 二、为什么是"分层预算"，不是一个总数

一个总数（"不超过 8000 token"）等于没有策略——超了就得随机砍。

分层之后每一层有自己的用途，砍的时候知道砍谁：

```
total 12000
├── system      800   固定指令，永不参与裁剪
├── goal        400   当前任务目标，永不参与裁剪
├── recent     8000   近期原文，从尾部往前填
└── tool_result 2400  工具结果，超长先压
```

**关键在"配额"这两个字**：它把"总量控制"变成了"每一类各占多少"，于是压缩时不用做价值判断——直接按类砍。

---

## 三、三条铁律

### 1. 目标锚点永不丢

最初那条 user 消息是最容易被压掉的东西（它最旧），也是最不能压的东西（它不可重建）。

**如果不保护会怎样**：任务跑到第 15 步，模型开始自由发挥——因为上下文里已经没有"用户到底要什么"了，只剩一堆工具结果。

代码里的体现：`goal_text` 在循环外算一次，压缩时永远保留那条消息。

### 2. 先压工具结果，后丢消息

工具结果通常占 60% 以上的 token，而信息密度最低——一段 3000 字的网页正文，模型真正要的可能是两句话。

而且它**可以重取**。所以第一刀砍这里，代价最小。

**压缩方式：保留头尾、省略中段。** 头（网址、参数）和尾（报错、结论）最重要，中间往往是重复内容。

### 3. 成组丢弃，绝不制造孤儿 tool_call

`assistant` 的 `tool_calls` 和紧随其后的 `tool` 消息是**一组**。删了结果留了调用，模型会看到"我调了工具但没返回"，然后重试或者编一个结果出来。

代码里的体现：`_group()` 把 `(assistant + 它的 tool 消息)` 当成原子单位，要么整组留、要么整组丢。

**这条最容易被忽略，也最容易被面试官抓。** 它属于"上下文结构不变式"，和数据库的引用完整性是一回事。

---

## 四、压缩手段的排序：为什么摘要在最后

| 手段 | 信息损失 | 成本 | 什么时候用 |
|---|---|---|---|
| 砍重复（同一页面读三次留最后一次） | 无 | 0 | **永远先做** |
| 工具结果头尾截断 | 低 | 0 | 第二 |
| 结构化抽取（提字段不压原文） | 低 | 0 | 第三 |
| 摘要 | **高** | 一次模型调用 | **最后** |

摘要最贵、最容易漂移——它会把"别删原文件"变成"注意文件安全"这种模糊表述。**能不用就不用。**

---

## 五、观测：少了第三个数字，前两个没有意义

每次压缩必须记三样：

1. `before_tokens` / `after_tokens` —— 省了多少
2. `dropped_messages` / `compressed_tools` —— 丢了什么
3. **压缩前后同一批任务的成功率** —— 有没有变差

**只有前两个，你只能证明"省了"；加上第三个，才能证明"没省坏"。**

代码里的体现：压缩记录会写成一条 `context_compression` step 落进任务账本，事后可以逐条核对。

---

## 六、这版实现的边界（要主动说）

- ❌ **没做摘要**：长任务里 user/assistant 也会累积，最终还是会爆，那时才需要滚动摘要
- ⚠️ **token 是估算的**：中文按 1 token/字、英文按 3.2 字符/token，实际偏差 ±10%，应该用 API 返回的 `usage.prompt_tokens` 校准
- ⚠️ **没有做"工具结果重取"的回路**：压缩提示里写了"可重新读取"，但模型没有对应的工具去展开
- ❌ **没有效果评估**：还没做"压缩 / 不压缩"的成功率对照

## 七、第三级：目标降级（已实现）

### 什么时候触发

压完工具、丢完成组中间消息，**仍然超预算**，且任务有 `task_id`。

### 它做什么

把目标原文**移出窗口**，替换成：

```
[任务目标已降级]
目标开头：把桌面上这三份文档整理成摘要并保存…
原文共 4120 字，完整内容请调用 read_task_original(task_id="abc123") 取回。
注意：执行删除/覆盖/发送等不可撤销操作前，必须先回查原文确认约束。
```

**注意：这是"移出窗口"，不是"删除"。** 原文还在 `tasks.description` 里。

### 为什么必须配一个回查工具

没有 `read_task_original`，那个 `task_id` 就是空头支票——模型看得到引用、拿不到内容，这一级就退化成**静默删除**。

所以这次同时加了第 29 个工具 `read_task_original(task_id)`，权限上 user / guest 都放行。**工具和降级是一起上的，不能只上其中一个。**

### 为什么不做"摘要"

摘要会重写语义，最容易丢**否定约束和例外条件**——"别动原文件，除非标了 revisit"很容易变成"保留原件"。

所以这里用的是**截断 + 显式指路**：留开头一句（通常是核心动词），其余让模型自己去取。**宁可让它多调一次工具，也不要让它相信一段我编的摘要。**

### 三条保护

1. **没有 task_id 就不降级**（有测试）：避免产生无法回查的引用
2. **降级文案里带"不可撤销操作前必须回查"**（有测试）：把风险提示写进上下文，而不是写在代码注释里
3. **降级要记进账本**：`goal_downgraded=true`、`goal_original_chars=4120`，事后能查是哪次任务降的级

### 还差的第四级

第三级只是"把目标搬出去"，任务本身还在同一个上下文里跑。真到极限需要**任务分段**：结束本段、开新上下文、只带一张交接单（目标 + 已完成 + 待办 + 关键产出）。

**那张交接单的数据我其实都有**（TaskManager 的 steps），缺的是生成和注入的机制。这是下一步。

## 八、会被追问的五个问题

**Q1：为什么按 token 不按轮数？**
一轮里可能塞了 3000 字网页，三轮就爆；而三条短消息可能才 200 token。按轮数是拍脑袋，按 token 才是按成本。

**Q2：压缩会不会把目标忘了？**
所以目标锚点单独占一块预算、永不参与裁剪。这是硬约束，不是"尽量"。

**Q3：为什么删消息要成组？**
因为 assistant 的 `tool_calls` 和 `tool` 结果靠 `tool_call_id` 配对。拆开就产生孤儿调用，模型要么重试要么编结果。

**Q4：怎么知道压缩没把效果压坏？**
同一批任务压缩前后各跑一遍，比成功率和平均 token。**没有这个对照，就只能说"省了"，不能说"没省坏"。**

**Q5：压缩和长期记忆什么关系？**
记忆存的是"跨轮次仍然成立的事实"（用户偏好），压缩管的是"这一轮发多少历史"。记忆不参与裁剪，所以两者互不干扰——**一个是持久层，一个是传输层**。
